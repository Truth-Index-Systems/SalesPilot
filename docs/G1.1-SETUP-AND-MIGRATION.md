# Genesis G1.1 — Setup and Migration

## Scope

This build implements production campaign launch only. It does not start company discovery or change the frozen campaign wizard design.

## Environment variables

Add these to local `.env.local` and Vercel Production/Preview as appropriate:

```env
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=

OPENAI_API_KEY=
OPENAI_MODEL_DEFAULT=
OPENAI_MODEL_STRATEGY=
OPENAI_MODEL_ANALYSIS=
OPENAI_MODEL_EMAILS=
OPENAI_MODEL_REPLIES=
OPENAI_MODEL_SUMMARIES=
```

Optional local-only persistence fallback:

```env
SALESPILOT_ALLOW_DEV_PERSISTENCE=true
SALESPILOT_DEV_ORGANISATION_ID=
SALESPILOT_DEV_USER_ID=
```

Never set `SALESPILOT_ALLOW_DEV_PERSISTENCE=true` in production.

## Migration order

Run manually in Supabase SQL Editor or through your normal migration workflow:

1. `supabase/migrations/0001_genesis_campaign_foundation.sql` for a new database.
2. `supabase/migrations/0002_genesis_g11_production_campaign_launch.sql`.

Do not run these automatically against production from this ZIP.

## Required membership data

Every production user must have an active membership:

```sql
insert into public.organisation_memberships (
  organisation_id,
  user_id,
  role,
  status
) values (
  '<organisation uuid>',
  '<auth.users uuid>',
  'OWNER',
  'ACTIVE'
);
```

Only `OWNER` and `ADMIN` can launch campaigns in G1.1.

## Authentication expectation

The application reads the current Supabase browser session from the standard `sb-<project-ref>-auth-token` cookie, verifies the access token through Supabase Auth, then resolves the first active organisation membership server-side. The browser never supplies a trusted organisation ID.

## Verification

After installing dependencies with a functioning npm registry:

```bash
npm ci
npm run typecheck
npm run genesis:check
npm run campaigns:check
npm run build
```

Then complete the production test script from the handover:

1. Sign in.
2. Analyse a public website.
3. Select a campaign.
4. Launch it.
5. Confirm redirect and refresh persistence.
6. Confirm the campaign appears in Campaigns.
7. Retry with the same idempotency key and verify one campaign and one outbox event.
8. Verify a user in another organisation cannot read the campaign.

## Important implementation notes

- Launch is one PostgreSQL transaction through `public.launch_campaign`.
- The function independently rechecks active `OWNER`/`ADMIN` membership.
- Idempotency is serialised with a transaction advisory lock.
- The outbox event is written exactly once within the transaction.
- Outbox and idempotency tables have no authenticated customer policies.
- Campaign list/detail queries derive organisation context from the authenticated user.
