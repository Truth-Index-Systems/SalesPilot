# MarketRoute MR-R1 Build 5 — Constraint Extraction

## Purpose

Build 5 turns the immutable Genesis seller context into a durable, campaign-scoped constraint contract so downstream MarketRoute stages stop inventing seller constraints independently.

## Constitutional boundary

CE-R1 and CE-R2 are unchanged. This release is an application integration layer only.

AI still owns semantics at the seller-understanding boundary. Build 5 performs no new AI interpretation: it deterministically projects already-accepted Business DNA into four CE-R2-compatible classes:

- `BOUNDARY`
- `SUPPORTING`
- `LIMITING`
- `UNKNOWN`

`CONTRADICTORY` remains available in frozen CE-R2 but is intentionally not generated by this seller-context projection; contradiction remains Truth/graph state rather than a MarketRoute seller assumption.

## Constraint semantics

Boundary contracts are deliberately narrow. A campaign must remain connected to an evidenced seller offering and to the selected immutable commercial objective. ICP preferences are not promoted to hard impossibility.

Supporting contracts preserve evidenced seller offerings.

Limiting contracts preserve stated ICP industry, size, geography, buyer-role and problem/pain scope as restrictions on preferred targeting rather than automatic rejection rules.

Unknown contracts preserve explicit Business DNA unknowns as unresolved research debt. Unknown is never converted to false.

## Persistence

New immutable table:

`public.campaign_genesis_t8_constraint_sets`

Each campaign owns one constraint set tied cryptographically to the Build 2 seller-context fingerprint. The persistence RPC rejects any attempt to mutate a previously persisted set.

New campaigns persist the seller context first and the constraint set immediately after it.

Build 2-4 historical campaigns are deterministically materialised on the first `GenesisSellerContext` read. This makes the upgrade backwards compatible without another AI call and without modifying the original immutable seller context.

## Downstream consumption

`GenesisSellerContext` now exposes `constraintSet`.

Company Discovery and Contact/Route Intelligence receive that exact stored set as `business.genesisConstraintContracts`. Their prompts explicitly prohibit reclassification or invention of seller constraints.

This does not yet replace company-fit, opportunity or route mathematics. Those migrations belong to MR-R2 through MR-R5. Build 5 establishes the immutable constraint input contract they will consume.

## API

`GET /api/genesis-t8/campaigns/:id/constraints`

returns the authenticated campaign's persisted constraint set.

## Success conditions

1. New campaign launch persists exactly one immutable constraint set.
2. Existing Genesis campaigns materialise the same deterministic set without AI spend.
3. Constraint set fingerprint is tied to the immutable seller-context fingerprint.
4. Boundary, Supporting, Limiting and Unknown buckets are persisted separately.
5. Company Discovery consumes the stored constraints.
6. Contact/Route Intelligence consumes the stored constraints.
7. No downstream stage may reclassify those seller constraints.
8. CE-R1 and CE-R2 files are unchanged.
